## How to read it

- **`auth.users` is not a TaskOrbit table.** It is Supabase Auth's
  table. `profiles.id` is both its primary key and a foreign key to
  `auth.users.id` (`on delete cascade`), so deleting an auth user
  deletes their profile. Every other user reference in the app points
  at `auth.users` too — `created_by`, `assigned_to`, `author_id`,
  `actor_id`, `recipient_id`, `generated_by` — and the app reads the
  display name from `profiles.full_name` (via `actor_display_name()`
  in notifications, or by joining `profiles` in server actions).
- **`workspaces` is the root of all authorisation.** Almost every
  table carries a `workspace_id` (directly, or via `project_id` →
  `projects.workspace_id` for tasks and comments). Every RLS policy
  ultimately asks "is this user a member of this workspace, and with
  what role?" through the SECURITY DEFINER helpers
  `is_workspace_member()` / `member_role()`. There is no cross-workspace
  read anywhere in the app, and the realtime channels are scoped the
  same way (see `docs/ARCHITECTURE.md` §5).
- **`tasks` references itself.** `parent_task_id` is a self-FK
  (`on delete cascade`): a subtask is a row in `tasks` with
  `parent_task_id` set. One level only — the `validate_task()` trigger
  rejects a subtask whose parent is itself a subtask, and the
  `parent_task_id <> id` check rejects self-reference. Deleting a
  parent deletes its subtasks.
- **`tasks.assigned_to` is `on delete set null`.** Removing a member
  (or deleting their auth user) unassigns their tasks instead of
  deleting the tasks. The `remove_workspace_member` RPC does this
  explicitly for open tasks first; completed tasks stay assigned as a
  historical record.
- **`comments` belong to a task, not to a project.** A comment on a
  subtask is a comment on that subtask's row; the notification trigger
  notifies the *task's* assignee + creator (the subtask's assignee is
  always the parent's, so this is the same person).
- **`activity_logs` is write-mostly, never edited.** Rows are written
  by triggers (`log_*_activity`) and by the two RPCs plus
  `lib/actions/team.ts` (invite created/revoked). There are no UPDATE
  / DELETE policies on it. The `project_id` / `task_id` columns are
  nullable on purpose: the 0006 fix writes DELETE events with NULL
  ids, because the FK would otherwise point at a row that no longer
  exists (that bug made task/project delete fail with 23503 in Part 1).
- **`notifications.entity_id` is a bare UUID, not a FK.** It points
  at a task, project or workspace depending on `entity_type`
  (`'task'` / `'project'` / `'workspace'`). A real FK cannot express
  "one of three tables", so the link is by convention and the UI
  resolves it by `entity_type`. The same is true of the
  `ai_summaries` scope: `project_id` and `user_id` are nullable and
  the uniqueness rule is enforced by a partial unique index that
  coalesces NULLs to the zero UUID.
- **AI tables are cache + ledger, not source of truth.**
  `ai_summaries` holds generated JSON (7-day expiry,
  `input_digest` for cache reuse); `ai_usage` holds counts and
  statuses only — no prompts, no model replies, no secrets.
  `daily_job_runs` is the cron idempotency ledger (one row per
  workspace + job + workspace-local date). All three are written only
  through SECURITY DEFINER RPCs; there are no direct INSERT policies.
  **Migration 0007 (these three tables) is written but NOT applied.**
- **Storage is not a normal table.** `storage.buckets` /
  `storage.objects` are Supabase Storage's own tables. The `avatars`
  bucket (0008, **written but NOT applied**) is public for reads;
  writes are restricted by storage RLS to objects whose first path
  segment is the caller's own user id
  (`<user-id>/avatar-<timestamp>.<ext>`). `profiles.avatar_url`
  stores the public URL of the object — the URL is the only link
  between `profiles` and `storage.objects`; there is no FK.

## Relationship notes (the ones that surprise people)

1. **A user can be in many workspaces, in different roles.**
   `workspace_members` has a unique `(workspace_id, user_id)` pair
   and a `role` per row. Manager of one workspace, developer in
   another is normal. There is exactly one manager per workspace in
   this version (the creator; the `prevent_last_manager_removal`
   trigger makes the last manager undeletable).
2. **Invitations are role-locked to developer.**
   `workspace_invitations.intended_role` has a CHECK constraint
   `intended_role = 'developer'`. There is no way to invite a manager.
3. **A task's workspace is derived, not stored.** `tasks` has no
   `workspace_id` column — it goes through `project_id` →
   `projects.workspace_id` (helper `project_workspace_id()` /
   `task_workspace_id()`). The RLS policies on `tasks` and `comments`
   use those helpers.
4. **Activity and notifications denormalise the workspace.**
   Both carry their own `workspace_id` so a workspace's feed / inbox
   can be read with one indexed query, without joining through
   projects.
5. **Profiles are auto-created.** `handle_new_user()` (trigger on
   `auth.users`) inserts a `profiles` row on signup, copying
   `full_name` / `avatar_url` from the signup metadata. There is no
   INSERT policy on `profiles` for clients (`profiles_insert_none`
   denies it) — the trigger is the only creator.
